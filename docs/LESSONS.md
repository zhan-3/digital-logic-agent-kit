# 本次实践提炼出的高价值约束

这些结论来自完整经历“课程镜像 → RTL/Testbench → Icarus → XSim → schematic → Implementation/Bitstream → Hardware Manager → 网页报告”的一次实践。它们不是某份个人答案，而是能减少误判的工程规则。

## 1. 任务名称不是真值表

- Lab 3 的“2 输入 4 位多路复用器”实际真值表选择加法/减法结果，失能输出固定值；按常见 MUX 直觉实现会错。
- ALU 页面表格看似高有效，课程 starter 和 Testbench 却定义五个操作键低有效；应以可执行接口、板卡电平和实际按键为裁决依据。
- 页面总览、具体任务页、旧截图和 starter 可能属于不同版本。任何“看起来应该如此”的假设都要变成可运行测试。

## 2. 引脚是四层映射

始终记录：

```text
RTL 端口 → XDC get_ports 名 → FPGA PACKAGE_PIN → 实物丝印
```

EGO2 实物 SW1–SW16 与常用 XDC 名 SW0–SW15 相差 1；端口名本身没有板级含义。`reset` 接 `K3` PIN 时，可能对应实物 K6，而不是“第三个按键”。

## 3. 证据链不可折叠

```text
本地自检 ≠ XSim
XSim ≠ RTL/Synthesis schematic
综合 ≠ Implementation/Timing
Bitstream ≠ Program 成功
Program 成功 ≠ 功能实测
本地通过 ≠ OJ Accepted
网页编辑完成 ≠ 暂存成功 ≠ 最终提交
```

状态表必须保留这些分界。这样 Agent 才不会把“能推断”写成“已观察”。

## 4. 穷举测试与报告波形分工不同

长自检负责覆盖，例如穷举 MUX、译码器和表决器；短场景波形负责教学解释，例如两组 ALU 输入逐项展示五种操作。不要为了截图牺牲覆盖，也不要把上千组自检波形塞进报告后无法阅读。

## 5. Vivado 自动化的三个陷阱

- 空约束数组不能生成 `read_xdc {}`；应只为实际文件输出命令。
- 建 `.xpr` 时使用 `create_project`、设置 fileset/top 并正常退出即可，不依赖错误的无参数 `save_project`。
- 组合顶层没有用户时钟路径时，Timing Summary 的 WNS/TNS 可能为 `NA`。这与“100 MHz 时序通过”不是同一句话。

脚本完成后还要检查目标文件存在，并读取 DRC/Timing，而不是只依赖 Vivado 退出码。

## 6. 硬件测试先用可辨识模式

- 先测试单比特，确认位序；再测边界值、进位/借位和移出位。
- 显示 `F0`、`30` 一类图案比随机数更容易发现某个拨码没拨到底。
- 低有效按键通常需要按住观察组合 ALU；松开回到默认结果是规格的一部分，不是故障。
- 下载新 Bitstream 会覆盖当前配置；切换模块前先记录需要的现象或照片。

## 7. 网页报告的真实保存检查

- CodeMirror 等编辑器会虚拟化 DOM，当前 `.cm-content.innerText` 可能只是可见片段；完整性要看预览区和关键段落。
- “暂存”后必须等待按钮状态恢复，再重新加载；重载后逐张确认图片实际加载。
- 登录过期或网络中断会使保存结果未知。重新认证后读取服务端内容，再决定是否重做。
- 最终提交应是单独的一次明确授权，不能从“帮我完善报告”推导出来。

## 8. 分享工程而不是分享身份与证据

最有复用价值的是目录布局、接口半成品、测试策略、脚本、板卡映射、故障语义和提示词。个人学号、完整个人报告、OJ 截图/提交号、Cookie/HAR 以及未经本人实测的结论既无通用价值，也会污染他人的证据链。
